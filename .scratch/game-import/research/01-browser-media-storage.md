# Research: Browser storage for imported per-question media
tracker: `.scratch/game-import/issues/01-research-browser-media-storage.md`
date: 2026-11-01
sources verified: yes

## Summary

| Option | Quota | Eviction risk | Persistence | API ergonomics | Angular (signals, zoneless) fit |
|---|---|---|---|---|---|
| **A. IndexedDB** | Shared origin quota: Chromium ~60% of total disk/origin; Firefox min(10% disk, 10 GiB group); Safari ~60% disk (Safari 17+) | Evicted only under storage pressure (LRU) or Safari 7-day inactivity rule | Best-effort by default; `persist()` supported in all three | Async, request/event-based; **Blob storable directly via structured clone**; wrappers recommended by web.dev but not required | Good — read once into a signal; moderate boilerplate |
| **B. OPFS** | Same shared origin quota as IndexedDB (storage endpoint `fileSystem`, quota `null`) | Same as IndexedDB | Same as IndexedDB | Async main thread (`createWritable` — **Safari 26+ only**); fast sync handles are **dedicated-worker-only**; read back via `getFile()` → `File` | Good but more code; needs a worker for Safari < 26 writes |
| **C. Data URLs in localStorage** | **5 MiB localStorage per origin** (10 MiB web storage total), values are UTF-16 strings; base64 inflates ~+33% | Highest: quota errors at ~3–4 MB of media; Safari 7-day rule applies; private modes clear it | Cleared at end of private sessions; 7-day ITP cap in Safari | Synchronous, string-only, whole-string rewrites, no streaming; `QuotaExceededError` on overflow | Worst — huge sync string ops on main thread; awkward around signals |
| **D. Cache API** | Shared origin quota (endpoint `caches`); `QuotaExceededError` on overflow | Best-effort everywhere; cleared wholesale per origin; Firefox private mode "may be unavailable" | Best-effort; `persist()` applies | `cache.put(url, new Response(blob))` / `cache.match(url)`; async; keyed by Request/URL — you invent keys; **secure context required** | Good — clean async fit with `toSignal`/`resource` |

For a quiz SPA storing "a few MB" of imported JPG/MP3 per game, **every one of the four options is far above quota needs in a normal browsing session** (hundreds of MB to GBs of per-origin quota). The real differentiators are (1) whether Blobs are first-class (IndexedDB, OPFS, Cache API — yes; localStorage — no), (2) eviction risk (all best-effort unless `persist()`; Safari's 7-day inactivity deletion hits all of them), and (3) code volume + Angular/zoneless fit. Evidence points to **IndexedDB as the primary store** (Blobs directly, simplest main-thread API, longest browser support), with OPFS as a viable alternative that costs more code on Safari, and **localStorage data URLs / Cache API as the worst fits** for media.

> **Which Angular is this research for?** This branch was cut from `master`, which still holds the *legacy* tree (`package.json` pins `@angular/core ~7.1.0` + zone.js 0.8). The app this feature targets is the rebuilt Angular 22 workspace on `develop` — standalone components, signals, zoneless (ADR `docs/adr/0001-angular-22-fresh-scaffold.md`; verified on `develop`: `src/app/game/layout/layout-with-score/question/question.ts` uses `inject()`, standalone `imports`, and its template uses `@if`/`@for`). Every "Angular 22 signals + zoneless fit" section below describes that target. On the legacy tree plain promise callbacks happen to just work, but that tree is not the destination of this feature.

## Context — what this storage must serve

- The Game JSON arrives by user file-picker import and is persisted as plain JSON under the localStorage key `games` (`const GAMES_KEY = 'games'` in `src/app/_services/data/local-storage/game.service.ts`, `develop` tree). Gameplay re-serializes that whole key on every score/answer update (`localStorage.setItem(GAMES_KEY, JSON.stringify(games))`), so the media mechanism must not inflate that value.
- Media hangs off `Question` as filename strings — `image?: string[]`, `sound?: string`, `answerImage?: string` (`src/app/_models/question.ts`) — and the question template resolves them against bundle assets today: `src="/assets/images/{{ img }}"`, `src="/assets/sounds/{{ question.sound }}"` (`src/app/game/layout/layout-with-score/question/question.html`). Once `assets/temp/` is gone, these bindings must point at blob object URLs resolved from the imported-media store instead.
- Sizes: "a few MB" of JPG/PNG + MP3 per Game; several Games can be installed at once, so tens of MB total is the realistic ceiling.
- System sounds (`public/assets/sounds/system/`) are app chrome and stay bundle-shipped — out of scope (`.scratch/game-import/map.md`).
- Zoneless nuance worth noting now: today's question component mutates plain class fields only from bound click handlers, which is safe under zoneless because bound listeners schedule change detection. The media read will be the first *async* callback in this component's render path — the case that must end in a signal write (see Option A's Angular-fit section).

## Option A — IndexedDB

### Quota and eviction
- IndexedDB is one of the origin-quota-managed "site storage" technologies. MDN lists IndexedDB alongside Cache API and the File System API (OPFS) as governed by each browser's storage management system, and a fill-quota write fails with `QuotaExceededError` ([MDN — Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- Per-browser numbers (same MDN source):
  - **Chromium:** origin limit ~60% of the *total* disk size, in both best-effort and persistent modes; the browser overall caps at ~80% of total disk. Quota is computed from total disk, not free space, to resist fingerprinting ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). web.dev agrees ("Chrome allows the browser to use up to 80% of total disk space. An origin can use up to 60%") and adds that in **incognito** Chrome reduces per-origin storage to ~5% of total disk, and to ~300 MB max if "Clear cookies and site data when you close all windows" is on ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)).
  - **Firefox:** best-effort origin limit is the smaller of 10% of total disk or a **10 GiB group limit** shared by all origins of the same site (eTLD+1); origins granted persistence get up to 50% of total disk capped at 8 TiB with no group limit ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). (web.dev's older Firefox figures — "up to 50% of free disk space" browser-wide, 2 GB eTLD+1 group — conflict with MDN's current numbers; treat MDN as current and web.dev's row as stale.)
  - **Safari:** since Safari 17 / macOS Sonoma / iOS 17, per-origin quota ~60% of total disk for browser apps (~15% for other WebKit-embedding apps), browser-wide cap 80% / 20%, no more user prompts; before that, Safari gave ~1 GiB and prompted for more in 200 MB increments ([WebKit — Updates to storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)). WebKit explicitly scopes this policy to "localStorage, Cache API, IndexedDB, Service Worker, and File System" — i.e., all four options in this document share it ([WebKit — Updates to storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)).
- Eviction, shared for all origin-quota storage: data is **best-effort by default**. Under storage pressure (or when the browser's overall cap is hit) the browser evicts whole origins **least-recently-used first**; eviction removes *all* of an origin's data at once (IndexedDB + Cache + OPFS together), never parts ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). web.dev's wording: Chromium and Firefox "will begin to evict data when [space runs out], clearing all site data from the least recently used origin first" ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)).
- Safari additionally **proactively deletes all script-writable storage of an origin after seven days of Safari use without user interaction** — the affected list explicitly includes IndexedDB (plus LocalStorage, SessionStorage, media keys, and service worker registrations and cache); home-screen web apps are exempt (they keep their own use counter) ([WebKit — Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). For a quiz game opened from time to time this is the single biggest data-loss risk on Safari.
- Over-quota writes: the IndexedDB **transaction aborts** and the `onabort` event carries a `DOMException` with `name === "QuotaExceededError"` ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)).

### Persistence
- Default is best-effort; `navigator.storage.persist()` requests the persistent bucket. Firefox **shows a permission prompt**; Safari and most Chromium browsers auto-approve/deny based on the user's interaction history, with no prompt ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). `persist()` is a promise resolving to a boolean and is **not available in Web Workers** ([MDN — StorageManager.persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)); `persisted()` reports the current mode ([MDN — StorageManager.persisted()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persisted)); `estimate()` reports quota/usage ([MDN — StorageManager.estimate()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate)). Support (MDN BCD): `persist`/`persisted` Chrome 55+, Firefox 57+, Safari 15.2+; `estimate` Chrome 61+, Firefox 57+, Safari 17+ ([BCD api/StorageManager.json](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json)).
- Spec semantics: persistent buckets should be exempt from automatic eviction ("the user agent must inform the user…"), and the spec requires that a quota not be a function of available storage space (anti-fingerprinting) ([Storage Standard](https://storage.spec.whatwg.org/)).
- Private/incognito: browsers "may apply different quotas, and stored data is usually deleted when the private browsing mode ends" ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)); Chrome incognito quota ~5% of total disk ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)).
- Empirically the Chrome team's research shows browser-initiated eviction of regularly-visited sites is very rare ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), referencing [web.dev — Persistent storage](https://web.dev/articles/persistent-storage)).

### API shape
- IndexedDB is a low-level, **transactional, object-oriented** database: you open a connection (`indexedDB.open()` returns an `IDBRequest`), define object stores in an `upgradeneeded` event, and do all reads/writes inside explicit transactions; operations are asynchronous and communicate via events on request objects ("asynchronous operations communicate to the calling application by firing events on `IDBRequest` objects") ([MDN — IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)).
- **No string-only constraint:** "any objects supported by the structured clone algorithm can be stored" — and `Blob`/`File` are structured-cloneable, so an imported JPG/MP3 can be stored as a Blob directly, alongside an indexed key like `gameId/questionId/kind` ([MDN — IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)). Blobs come back as Blobs; feed them to `URL.createObjectURL()` for display ([MDN — Blob](https://developer.mozilla.org/en-US/docs/Web/API/Blob)).
- The verbosity is the main ergonomic cost: web.dev explicitly recommends a small promises wrapper ("use IndexedDB (with a promises wrapper)"; "it is event-based, so storing low-complexity data requires significant setup") ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)). Community wrappers such as `idb` exist; none are framework-dependent and the dependency is optional.
- IndexedDB is available in window and workers ([MDN — IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)).

### Angular 22 signals + zoneless fit
- Async pitfall: a `.then()`/`await` callback that writes to a **plain class property** will not re-render a zoneless app — there is no ZoneJS patching to trigger change detection. Zoneless CD is scheduled by, among other things, "Updating a signal that's read in a template"; `NgZone.onStable`/`onMicrotaskEmpty` "will never emit" in zoneless apps ([angular.dev — Zoneless](https://angular.dev/guide/zoneless)). Writing a **signal** from the promise callback is therefore the mechanism — not `NgZone.run` (still supported but not the tool for this).
- Recommended read pattern: a `resource()` whose `loader` opens the transaction and returns the Blob (or an object URL); the component renders from `res.value()` with `status()` for loading/error UI. `resource()` is exactly Angular's documented bridge "to incorporate async data into your application's signal-based code and still allow you to access its data synchronously" ([angular.dev — Async reactivity with resources](https://angular.dev/guide/signals/resource)) and is listed as stable since v22 ([angular.dev API — resource](https://angular.dev/api/core/resource)). If the store is exposed as RxJS Observables, `toSignal` / `rxResource` from `@angular/core/rxjs-interop` are the documented equivalents ([angular.dev — RxJS Interop](https://angular.dev/ecosystem/rxjs-interop)).
- Blob → template: resolve the Blob, then `this.url.set(URL.createObjectURL(blob))` into a `signal<string>`, bound as `<img [src]="imgUrl()">` / `<audio [src]="soundUrl()">`. Create Blob URLs only as needed: "Each of these must be released by calling `URL.revokeObjectURL()` … As long as there's one object URL active, the underlying object cannot be garbage-collected" ([MDN — blob URLs / memory management](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob)); the create/revoke pair is documented at ([MDN — URL.createObjectURL()](https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static), [MDN — URL.revokeObjectURL()](https://developer.mozilla.org/en-US/docs/Web/API/URL/revokeObjectURL_static)).
- Revoke lifecycle: revoke in `effect((onCleanup) => …)` — the documented cleanup hook "invoked before the next run of the effect begins, or when the effect is destroyed" ([angular.dev — Effects](https://angular.dev/guide/signals/effect)). Do **not** revoke in the media element's `load` event: MDN flags revoke-on-render as an anti-pattern because it breaks later user interactions (right-click-save, open-in-tab); revoke only when the resource is no longer reachable by the user. Browsers do release object URLs automatically at document unload, so a leak is bounded by the page lifetime ([MDN — blob URLs](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob)).
- Cache the object URL per media item (e.g. in a `linkedSignal` keyed on `gameId/questionId`) instead of re-creating per CD pass.

## Option B — OPFS (origin-private file system)

### Quota and eviction
- OPFS is a File System Standard storage endpoint reached via `navigator.storage.getDirectory()`. MDN: "The OPFS is subject to browser storage quota restrictions, just like any other origin-partitioned storage mechanism (for example IndexedDB). You can access the amount of storage space the OPFS is using via `navigator.storage.estimate()`" and "Clearing storage data for the site deletes the OPFS" ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)). In the Storage Standard model it is registered as an endpoint (`fileSystem`) whose quota is `null` — meaning it shares the origin shelf quota rather than having its own number ([Storage Standard](https://storage.spec.whatwg.org/)); the File System Standard likewise defines it as "a storage endpoint whose identifier is `fileSystem`, whose quota is null" ([File System Standard](https://fs.spec.whatwg.org/)).
- Quota numbers and over-quota behavior are therefore identical to IndexedDB: Chromium ~60% of total disk/origin, Firefox min(10% disk, 10 GiB group), Safari ~60% disk / 17+, `QuotaExceededError` on overflow ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebKit — Updates to storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)).
- Eviction: same LRU best-effort eviction and the same Safari 7-day inactivity deletion as every other script-writable store — WebKit's 7-day list covers "the storage types created by storage APIs: localStorage, Cache API, IndexedDB, Service Worker, and File System" ([WebKit — Updates to storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/); [WebKit — Full Third-Party Cookie Blocking](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/); [MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).

### Persistence
- Same `persist()`/`persisted()`/`estimate()` surface as IndexedDB — `getDirectory()` itself lives on `StorageManager`, in the same secure-context API family ([MDN — StorageManager.getDirectory()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/getDirectory), [MDN — Navigator.storage](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/storage)).
- No picker or user gesture is involved: OPFS is "private to the origin of the page and not visible to the user", with no permission prompts — unlike `showOpenFilePicker()` ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)).
- Private browsing: `getDirectory()` throws `SecurityError` "in some browsers if … called in private browsing mode", or `UnknownError` for the same reason ([MDN — StorageManager.getDirectory()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/getDirectory)).

### API shape
- **Support gates (MDN BCD, [api/StorageManager.json](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json), [api/FileSystemFileHandle.json](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemFileHandle.json)):**
  - `navigator.storage.getDirectory()` / `getFile()` / `createSyncAccessHandle()`: **Chrome 86+** (Chrome Android 109+), **Safari 15.2+**, **Firefox 111+**.
  - `createSyncAccessHandle()` is added in Chrome 102 / Safari 15.2 / Firefox 111 and per MDN is "only usable inside **dedicated Web Workers** for files within the origin private file system" ([MDN — FileSystemFileHandle.createSyncAccessHandle()](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createSyncAccessHandle)). The fetch was Chrome 86→102 era (sync access handles were OPFS-optimized additions); Chrome 108 / Safari 16.4 fixed the early spec bug where `close()`/`flush()`/`getSize()`/`truncate()` were async instead of synchronous (BCD "sync_version" entries; MDN note on the getDirectory page) ([MDN — StorageManager.getDirectory()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/getDirectory)).
  - **`createWritable()` (async `FileSystemWritableFileStream` on the main thread): Chrome 86+, Firefox 111+, but Safari only from Safari 26** (BCD `version_added: 26`), matching the WebKit Safari 26.0 release note "support for the File System WritableStream API, enabling direct writing to files" ([WebKit — WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). **Consequence: on Safari 15.2–25.x you can only write OPFS files from a dedicated worker via `createSyncAccessHandle()`** (worker + byte-buffer write), which is the documented worker pattern ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)).
- Main-thread write path (modern browsers): `getFileHandle(name, {create:true})` → `createWritable()` → `write(...)` → `close()`; the write accepts a `Blob` among other data types ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system), [File System Standard](https://fs.spec.whatwg.org/)).
- Read path: `getFileHandle()` → `getFile()` returns a `File`, "a specialized type of `Blob`… can be manipulated just like any other `Blob`" — so `URL.createObjectURL(file)` works for `<img>`/`<audio>` display ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)).
- Deleting: `directoryHandle.removeEntry(name)` or `handle.remove({recursive:true})`; MDN shows a one-liner to wipe the whole OPFS root ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)).
- Caveats: exclusive file locks — a `createSyncAccessHandle()` blocks `createWritable()` (and vice versa) until closed ([MDN — createSyncAccessHandle()](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createSyncAccessHandle)); UNVERIFIED: community reports exist of Safari failing to render `<img>`/`<audio>` from Blob URLs of OPFS-backed `File`s in some versions, but I could not find a primary WebKit source documenting it — verify on target Safari versions before relying on it.

### Angular 22 signals + zoneless fit
- Same async/signal integration story as IndexedDB: `resource()` loader resolving to an object URL, signal writes from promise callbacks to drive zoneless CD ([angular.dev — Async reactivity with resources](https://angular.dev/guide/signals/resource), [angular.dev — Zoneless](https://angular.dev/guide/zoneless)).
- Extra code vs IndexedDB: file-name management (`${gameId}/${questionId}.jpg`), create flags, explicit `close()`/error handling, and (for Safari < 26) a dedicated worker for writes. That worker's result still reaches the component as a normal promise/observable → signal write, so no zoneless change is needed ([angular.dev — Zoneless](https://angular.dev/guide/zoneless)).
- Blob URL lifecycle is identical (create → bind `[src]` → revoke in `effect(onCleanup)`) ([MDN — blob URLs](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob), [angular.dev — Effects](https://angular.dev/guide/signals/effect)).

## Option C — Data URLs in localStorage

### Quota and eviction
- localStorage is **5 MiB of local storage plus 5 MiB of session storage per origin — 10 MiB web storage total "on all browsers"** ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). The HTML spec sets no number: it requires `setItem` to "throw a `QuotaExceededError`" if the value cannot be stored, leaving the limit implementation-defined ([HTML Standard — Web storage](https://html.spec.whatwg.org/multipage/webstorage.html)).
- Values are strings: "The keys and the values stored with `localStorage` are in the UTF-16 string format" ([MDN — Window.localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)). A JPG/MP3 must be base64-encoded: RFC 4648 base64 encodes each 24-bit group (3 bytes) as 4 characters, i.e. ~+33% size before any other overhead ([RFC 4648 §4](https://www.rfc-editor.org/rfc/rfc4648.html)). Practical budget: roughly 3–4 MB of binary media max per origin *before* counting the game JSON. Historical per-browser localStorage tables (Chrome 10 MB, Firefox 5 MB, Safari 5 MB) vary by version; current MDN states the 5 MiB/10 MiB numbers — older per-browser figures are UNVERIFIED here.
- Over-quota: `setItem()` throws `QuotaExceededError` ("Thrown if the storage run out of disk quota or the user declined to grant you more space") ([MDN — Storage.setItem()](https://developer.mozilla.org/en-US/docs/Web/API/Storage/setItem)); because writes are whole-string replacements, updating one game's image re-writes the entire several-MB string ([MDN — Using the Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)).
- Eviction/persistence: localStorage has no quota sharing with the big stores — it is a fixed 5 MiB — and it is squarely inside Safari's 7-day script-writable-storage deletion ("deleting all of a website's script-writable storage after seven days of Safari use without user interaction on the site", list including "LocalStorage") ([WebKit — Full Third-Party Cookie Blocking](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). (The 7-day cap idea first appeared for client-side cookies in ITP 2.1 ([WebKit — ITP 2.1](https://webkit.org/blog/8613/intelligent-tracking-prevention-2-1/)) and was extended to all script-writable storage in the later post cited above.)
- Private/incognito: "In private mode, `localStorage` is treated like `sessionStorage`… all data stored in the private window is deleted when the browser or browser tab is closed" ([MDN — Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)).

### Persistence
- Normal mode: persists across sessions with no expiry ([MDN — Window.localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)). No `persist()` mechanism exists for Web Storage specifically; the 5 MiB cap is fixed. `navigator.storage.persist()` does not raise it (UNVERIFIED — no documented interaction).
- Privacy mode: data dies with the session (see above). Feature detection must handle browsers returning a zero-quota or throwing storage object in private mode ([MDN — Using the Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)).

### API shape
- "Both `sessionStorage` and `localStorage` in Web Storage are synchronous in nature… blocking the execution of other JavaScript code until the operation is completed"; MDN explicitly warns about large data and points to IndexedDB as the async alternative ([MDN — Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)).
- String-only: "`Storage` only supports storing and retrieving strings" — no Blob path; you encode to data URL and decode back for display ([MDN — Storage.setItem()](https://developer.mozilla.org/en-US/docs/Web/API/Storage/setItem)). No streaming and no partial reads: `getItem()` materializes the whole multi-MB string each time ([MDN — Using the Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)).
- "Data URLs … allow content creators to embed small files inline in documents" and blob URLs exist precisely because "data URLs embed resources in themselves and have severe size limitations" ([MDN — data: URLs](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/data), [MDN — blob: URLs](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob)). Per-browser hard caps on data URL length are UNVERIFIED (no primary numbers found).
- Ergonomic plus: no schema/versioning/transactions to manage — trivially simple for the *game JSON*, which is exactly the kind of small string data MDN deems suitable.

### Angular 22 signals + zoneless fit
- Since access is synchronous, there is no async-callback/change-detection hazard — a getter can read localStorage inline. The problems are the opposite: multi-MB base64 strings flowing through signals and templates hurt memory and GC; synchronous access blocks the main thread ([MDN — Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)).
- A data URL can be bound directly (`<img [src]="dataUrl()">`) — no object URL creation/revocation needed, so no `effect(onCleanup)` lifecycle. But every question's data URL living in localStorage on top of the JSON risks `QuotaExceededError` at import time with only a few MB of media — a hard failure with no graceful path ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- The storage-event cross-tab sync (`storage` fires only on *other* documents of the origin) is unique to Web Storage ([MDN — Using the Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)).

## Option D — Cache API

### Quota and eviction
- The Cache API provides "a persistent storage mechanism for `Request`/`Response` object pairs", exposed to window and workers, defined in the Service Workers spec but usable without a service worker ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)). It is one of the origin-quota-managed technologies, counted by `navigator.storage.estimate()`, and the browser "may delete the `Cache` storage for an origin… generally delete all of the data for an origin or none of it" ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)). Quota numbers are the shared origin ones (Chromium 60% disk/origin etc.) and over-quota `put()` rejects with `QuotaExceededError` ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)).
- Eviction: best-effort, whole-origin LRU under storage pressure, Safari 7-day rule — the WebKit 7-day list explicitly includes "Service Worker registrations and cache", and web.dev's best-effort list includes "IndexedDB, Cache API, etc." ([WebKit — Full Third-Party Cookie Blocking](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web), [MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). Firefox treats it like any other origin storage (best-effort unless `persist()`); MDN's older guidance that Firefox may make `CacheStorage` "unavailable in private mode" remains documented on the CacheStorage page ([MDN — CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage)).
- Note: unlike HTTP cache entries, "items in a `Cache` do not get updated unless explicitly requested; they don't expire unless deleted" — and "the caching API doesn't honor HTTP caching headers" ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)).

### Persistence
- **Window availability without a service worker (MDN BCD, [api/Cache.json](https://github.com/mdn/browser-compat-data/blob/main/api/Cache.json), [api/CacheStorage.json](https://github.com/mdn/browser-compat-data/blob/main/api/CacheStorage.json)):** Chrome 43+ on window (40–43 was service-worker-only; "from version 43, all worker types and the main thread are supported"), **Firefox 41+ on window** (worker support from 44), **Safari 11.1+** — window and workers share the same `version_added`. The Service Workers spec itself mandates it: "The user agent must create a `CacheStorage` object when a `Window` object or a `WorkerGlobalScope` object is created" ([Service Workers spec](https://w3c.github.io/ServiceWorker/)).
- **Secure context required** (BCD "Secure context required": Chrome 65+, Firefox 44+, Safari 11.1+): "`CacheStorage` always rejects with a `SecurityError` on untrusted origins (i.e., those that aren't using HTTPS…)" ([MDN — CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage)). If this SPA is ever opened from plain `http://` (not localhost) this option dies; `file://` behavior varies by browser — UNVERIFIED.
- Private browsing: Firefox "may be unavailable in private mode" ([MDN — CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage)); Chrome incognito quota ~5% of total disk ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)).
- `persist()`/`estimate()` apply to the origin as a whole, so Cache API data benefits from persistent-bucket protection like everything else ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).

### API shape
- Write: `const cache = await caches.open('game-media-v1'); await cache.put('media/game1/q3/sound.mp3', new Response(blob, { headers: { 'Content-Type': 'audio/mpeg' } }));` — `cache.put()` "takes both a request and its response and adds it to the given cache"; the first argument can be a URL string or a `Request` ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)). There is no natural key for an *imported* file with no HTTP origin — **you must invent URL keys** and a Response wrapper, since the API is "keyed by request" and matching depends on URL + VARY semantics ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)).
- Read: `const res = await cache.match(url); const blob = await res.blob();` — a clean two-call async path, then `URL.createObjectURL(blob)` ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache), [MDN — Blob](https://developer.mozilla.org/en-US/docs/Web/API/Blob)).
- Design intent is HTTP-response caching "tied to the service worker model" (web.dev recommends it "for the network resources necessary to load your app") — offline-imported media is an off-label use ([web.dev — Storage for the web](https://web.dev/articles/storage-for-the-web)). Calling `put()` consumes the body, so clone if reused ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)).
- You own cache lifecycle: version cache names and delete stale caches yourself (MDN's versioned-cache example) ([MDN — Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache)).

### Angular 22 signals + zoneless fit
- Same pattern as IndexedDB: `resource()`/`toSignal` over the async match, signal writes from promise callbacks for zoneless CD ([angular.dev — Async reactivity with resources](https://angular.dev/guide/signals/resource), [angular.dev — Zoneless](https://angular.dev/guide/zoneless)). Ergonomically it is actually the *nicest* of the async options (open → put/match, no schema/transactions).
- Blob URL lifecycle identical to Option A (create → `[src]` → revoke in `effect(onCleanup)`) ([MDN — blob URLs](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob), [angular.dev — Effects](https://angular.dev/guide/signals/effect)).
- The secure-context requirement is the main Angular-agnostic risk: the app "runs offline", and any non-HTTPS, non-localhost delivery makes `caches` unusable ([MDN — CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage)).

## Recommendation

**Primary mechanism: IndexedDB.** Store each imported JPG/MP3 `File` as a Blob in a dedicated `media` object store, keyed by a stable media id — a content hash is ideal, since it dedupes identical files shared across questions/Games and survives re-import. The Game JSON keeps only those id references, so it stays a small JSON string in localStorage under `games` (as charted in `map.md`), and the frequent `setItem` re-serialization never touches media bytes. Evidence for IndexedDB over the alternatives:

1. **Quota headroom is a non-issue for all four options** at "a few MB per game" — every origin-quota store offers hundreds of MB minimum on desktop. The failure mode that actually bites is localStorage's fixed 5 MiB shared with base64 inflation: one or two games' worth of MP3s and it starts throwing `QuotaExceededError` with no recovery ([MDN — Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648.html)). That rules out Option C for media (fine for small settings).
2. **Blobs are first-class in IndexedDB** via structured clone — store the imported `File` objects directly, no encoding ([MDN — IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)). OPFS and Cache API also handle Blobs but with more ceremony (locks/worker writes; Response wrapping + invented URL keys).
3. **Browser support is the widest and oldest** for IndexedDB, and its main-thread API works identically on every engine. OPFS is excellent on Chromium/Firefox but **Safari cannot write OPFS from the main thread before Safari 26** — a dedicated-worker + `createSyncAccessHandle()` implementation is mandatory for Safari 15.2–25 ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemFileHandle.json), [WebKit — Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). Cache API needs a secure context everywhere ([MDN — CacheStorage](https://developer.mozilla.org/en-US/docs/Web/API/CacheStorage)).
4. **Eviction risk is equal for A/B/D** (shared origin shelf, LRU best-effort, Safari 7-day) — so it doesn't differentiate; it argues only for calling `navigator.storage.persist()` once after the first successful import, and for a UI hint if `persisted()` is false ([MDN — StorageManager.persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)).
5. **Zoneless/Angular integration cost is identical** for the async options (resolve → object URL → signal → `effect(onCleanup)` revoke), so the tie-breakers are support matrix and code volume, both favoring IndexedDB.

**OPFS becomes attractive** only if the app later grows to large per-file data with streaming/partial reads (in-place updates, big files) — that is its documented sweet spot ([MDN — Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)). **Cache API** is a reasonable secondary if the media should also be served transparently to `<img>`/`<audio>` via URLs without JS plumbing — but for a no-backend, file-import SPA that benefit does not materialize.

**Hygiene to apply regardless of store:**
- Call `navigator.storage.persist()` once after the first successful import, and surface a settings hint when `persisted()` returns `false` — that is the only lever that moves media out of the evictable best-effort bucket ([MDN — StorageManager.persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)).
- Pre-flight each import with `navigator.storage.estimate()` and warn before writing when the pack exceeds remaining headroom ([MDN — StorageManager.estimate()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate)).

**Fallback story for oversized packs** (a write rejects with `QuotaExceededError`, or `estimate()` shows the pack cannot fit):
1. **OPFS is explicitly *not* the fallback.** It shares the same origin shelf as IndexedDB (`fileSystem` endpoint, quota `null`), so moving bytes there frees nothing ([Storage Standard](https://storage.spec.whatwg.org/), [MDN — OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)). Its value is streaming/memory shape, not quota.
2. **Ladder within the origin quota:** first show per-Game sizes (records + `estimate()`) and let the user delete other Games to make room.
3. **Chromium-only escape hatch that genuinely exits origin quota:** the File System Access API — the user picks a real directory, media files stay on disk, and the `FileSystemDirectoryHandle` is persisted (in IndexedDB) and re-permissioned on return. Unsupported in Firefox/Safari; `map.md` already tracks "File System Access API / directory-picker support limits" as a separate question.
4. **Graceful degradation:** import the Game JSON *without* its media — question templates hide missing images and skip/replace missing sounds (the system "NoAnswer" sound path exists for chrome) — and the export/backup story (ticket 06) re-links media later.
5. **Slightly-over packs** may be re-encoded at import (downscale images, lower MP3 bitrate) instead of rejected — decision deferred to the storage-mechanism implementation ticket 05.

Open items this research could not settle (see UNVERIFIED marks above): Safari's rendering of blob URLs for OPFS-backed Files, whether `persist()` exempts a site from Safari's 7-day inactivity deletion, and `file://` delivery behavior for secure-context-only APIs (Cache API, `navigator.storage`). If the app is ever served from plain `http://` (not localhost), Option D dies outright and Options A–C keep working; `file://` needs a targeted check per browser.
